# Week 34 - 2026-08-22

## Decisions

- **[D050] Use compact exact postings as the DuckDB-free position-index
  candidate.** Format v5 moved result and Elo metadata to one record per game,
  grouped occurrences by game, compressed the per-hash directory, and streamed
  merged postings directly to staging. Format v6 then removed derivable offsets,
  stored 40-bit hash-delta lows with sparse exceptions, and omitted occurrence
  counts when they equal distinct-game counts. The current 1M artifact is 1,035
  MiB and postings-only import is 66.618 seconds at 1,404 MiB peak RSS. Rejected:
  preserving the 3,196 MiB fixed-width postings format, because it took 95.272
  seconds and peaked at 5,962 MiB.

- **[D051] Keep the opening-tree index optional.** The tree gives sub-millisecond
  warm public navigation and makes the starting position approximately 3,400x
  faster than postings replay, but it raises the current 1M postings import from
  66.618 seconds to 105.199 seconds. Rejected: enabling it by default before its
  product value justifies the 38.581-second build cost.

- **[D052] Defer shared board-transition replay until the post-merge profile
  justifies it.** A full transition tape would add about 0.8-0.9 GiB of payload
  and substantial sequential traffic. Builders already run sequentially, and
  the current larger postings costs are the 17.071-second external merge and
  6.787-second spill phase. Rejected: introducing a tape before measured
  sort/merge and publication work, because replay sharing does not solve a
  current overlapping-builder RSS problem.

- **[D053] Treat the literal default's dual derived build as the next product
  decision.** `import_config {}` currently enables both DuckDB rebuilding and
  exact postings, producing a measured 102.734-second 1M import. A DuckDB-free
  postings candidate takes 66.618 seconds, but the default must not change until
  exact position search, filters, deep traversal, fallback behavior, mutation,
  recovery, and existing-bundle compatibility are inventoried. Rejected:
  flipping the flag solely from benchmark evidence, because remaining DuckDB
  dependencies would become correctness regressions.

- **[D054] Make exact postings the production import default.** The query and
  lifecycle inventory confirmed that postings cover exact and filtered search,
  opening statistics, Elo distributions, deep traversal, reopen, invalidation,
  and recovery, while explicit and legacy DuckDB bundles retain their fallback.
  Three isolated 1M Release runs measured 81.359-81.728 seconds, with an 81.520
  second median, 20.6% faster than the old 102.734-second dual-build default.
  Rejected: using the 66.959-second same-process comparison result as the default
  benchmark because an unexplained 14.561-second process/order gap remains.

- **[D055] Stop provisioning DuckDB for normal persistent bundles.** New and
  postings-covered bundles now create and open without `positions.duckdb`.
  Postings-only repair rebuilds directly from canonical SQLite and fails closed
  if publication cannot complete. Existing DuckDB-only bundles retain one
  release of fallback support and attempt a staged, non-destructive migration.
  Rejected: creating an empty DuckDB file when postings repair fails, because
  that could silently serve empty results as if the fallback were synchronized.

- **[D056] Complete the release-boundary DuckDB removal without reading legacy
  files.** Legacy bundles rebuild postings from canonical SQLite and leave any
  `positions.duckdb` untouched; scratch databases use private temporary bundles,
  and deterministic expected fixtures replace DuckDB oracles. Rejected: keeping
  DuckDB linked solely to read a derived file whose canonical source remains
  available, because that would extend the dependency without protecting user
  data.

## Learned

- The current 1M postings-only import spends 14.244 seconds ingesting, 8.880
  seconds deduplicating, 12.270 seconds replaying, 6.787 seconds spilling, and
  17.071 seconds merging. Comparison sort plus the 85-way merge is the largest
  algorithmic target.
- Postings format v6 shrank the directory by 178,958,640 bytes, or 21.6%, but
  only modestly improved build time. Directory and final serialization now cost
  about two seconds, so another format micro-optimization has limited wall-time
  upside.
- Measured postings builder phases leave 5.289 seconds in validation, reopening,
  checksum, publication, cleanup, and other orchestration. Instrument those
  operations separately before attempting checksum fusion or reader reuse.
- A fast internal reader did not guarantee a fast product path. The raw opening
  tree was already near 5 us p50 while the public starting-position query took
  about 3.2 seconds because correctness required full postings replay.
- Persisting and validating completeness for one high-value root fixed the
  starting position without weakening the general shallow-tree boundary.
- Reusing postings distinct-game counts removed 84 tree child spill runs and
  reduced postings-plus-tree import by about 15% without changing query
  semantics.
- The project performance helper expects test binaries under `<build-dir>/test`,
  while this Release build places them under `build/perf-release/bin`. Direct
  binary invocation is the verified benchmark path for this worktree.
- The postings build is process-context sensitive: a contemporaneous serialized
  comparison measured 66.959 seconds and 1,110 MiB peak RSS, while three isolated
  literal-default runs clustered at 81.359-81.728 seconds. This 14.561-second
  median gap is too large for normal variance and is not yet attributed.
- A generic dirty flag cannot stand for DuckDB synchronization once DuckDB is
  optional. Clean recovery is now established by either synchronized DuckDB or
  checksum-verified postings covering the canonical SQLite game set.

## Problems and Solutions

- **Problem:** The first compact postings format still retained an 828 MiB
  directory for 68.9 million distinct hashes.
  **Solution:** Format v6 removed redundant offset deltas, used fixed 40-bit hash
  lows with sparse high exceptions, and omitted nearly all occurrence counts.
  The directory is now 649,481,128 bytes.
- **Problem:** The public starting-position explorer still took seconds after
  adding a summary-count fast path.
  **Solution:** Preserve the max-ply correctness check and mark only the
  canonical starting root complete after aggregating all of its occurrences.
  The public path can now trust that root without full replay.
- **Problem:** Tree construction independently rebuilt child distinct-game
  counts already stored in postings, creating 84 spill runs and an expensive
  merge.
  **Solution:** Stream sorted postings summaries into manager-backed tree
  construction while retaining the independent standalone path as an oracle.
- **Problem:** The benchmark name `default fast path` concealed that the default
  now performs both DuckDB and postings builds.
  **Solution:** Run the literal default separately, record its 102.734-second
  result, and make storage-path selection tomorrow's explicit decision.
- **Problem:** The rebuilt literal-default benchmark was consistently about
  14.6 seconds slower in a fresh process than the postings case inside the
  serialized comparison.
  **Solution:** Record both contexts, select the isolated 81.520-second median
  as the production number, and leave attribution as follow-up rather than
  treating the warmer comparison result as interchangeable.
- **Problem:** Opening a bundle with missing postings and no legacy DuckDB could
  create an empty `positions.duckdb`; a subsequent migration failure would leave
  an apparently available but semantically empty fallback.
  **Solution:** Detect whether the legacy file existed before opening it. Repair
  postings-only bundles directly from SQLite and fail open closed if publication
  fails; only pre-existing DuckDB files qualify as compatibility fallbacks.
