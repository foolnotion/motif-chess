# Week 33 - 2026-08-16

## Decisions

- **[D048] Run one root-workspace clangd service through the Motif Chess Nix shell.**
  The top-level `opencode.json` starts Clangd 21 from `motif-chess`'s Nix development shell, while each
  C++ repository's `.clangd` file selects its own `build/dev/compile_commands.json`. This gives agents
  an ecosystem-level LSP without depending on the ambient shell or collapsing the projects into one
  CMake build. Rejected: a root CMake project, because the libraries retain independent build and
  packaging contracts; per-agent manual `nix develop`, because it makes symbol resolution depend on
  how a session was started.

- **[D049] Materialize opening continuation statistics with separate direct and transposition counts.**
  `opening_continuation` stores one row for each `(root_hash, encoded_move, child_hash)` edge and is
  rebuilt transactionally with the DuckDB position store. The HTTP `frequency` field retains its
  existing any-path meaning, while `direct_frequency` reports games that chose the displayed
  continuation. The rollup is ordered by `root_hash` so DuckDB can prune row groups for a position
  lookup. Rejected: keeping the request-time self-join, because high-fanout positions
  produced a 321-706ms p99 on the 1M corpus; replacing direct frequency with global child popularity,
  because that would obscure the move-choice signal needed for preparation.

## Learned

- **Materialization alone did not make the read path fast.** The first unordered rollup run reduced
  p99 to 21.2ms but raised p50 to 15.1ms. Sorting `opening_continuation` by `root_hash` reduced the
  final sampled run to 2.95ms p50 and 6.74ms p99. Physical layout remains part of the query contract
  for large DuckDB tables.

- **Direct frequency and transposition popularity answer different repertoire questions.** A direct
  count answers what opponents played from the displayed board. Child-position popularity answers how
  common the resulting structure is across move orders. Presenting both prevents a transposition from
  making a rarely selected move appear to be the usual continuation.

- **Rollups must never be served after incremental position changes.** Inserts, deletes, and Elo
  updates drop the materialized tables. Until the next rebuild, the explorer uses the exact dynamic
  query, which preserves correctness for manual game edits.

## Problems and Solutions

- **Problem:** The request-time opening-stats query self-joined the dense position table and aggregated
  child positions globally. A few common positions dominated latency.
  **Solution:** Build `opening_continuation` and `position_summary` during rebuild. The unfiltered
  explorer reads the compact, root-hash-ordered rollup; filtered searches retain the dynamic path.

- **Problem:** A single count overloaded two different meanings: direct move selection and transposed
  child-position popularity.
  **Solution:** Preserve the public any-path count as `frequency` and expose the direct edge count as
  `direct_frequency`.

## Open Questions

- The measured results cover 989,967 games from `twic-1m.pgn`; repeat the benchmark on the 10M corpus
  before claiming the formal production target.

- Filtered explorer requests still use the dynamic candidate-ID path. Measure filter selectivity and
  tail latency before deciding whether a filter-aware DuckDB projection is justified.

- The root-hash ordering decision needs import/rebuild cost and on-disk-size measurements. The current
  benchmark measures query latency, not the full storage tradeoff.
